# 24 · 打标与检索

> 这一篇讲「记录怎么被打上标签，标签又怎么被搜出来」——AI 搜索与整理的地基。
> 2026-09-27 落地。技术内容以 [`app/`](../app/) 真实代码为准。

## 一 统一打标管道：写入先落本地，再异步增强
四条采集路径（照片-快门 / 照片-相册 / 声音 / 一句话）都从同一个口子打标：

```
draft（采集信号：text / sceneHint / blob / exif / visual / audio）
  ├─ A 规则层    extractTags(draft)      同步 · 离线 · 永不失败
  ├─ B 元数据层  deriveLocalTags(draft)   同步 · 离线 · 永不失败（在 A 之上补 scene）
  ▼
repo.addEntry → Entry(本地标签, tagSource='rule', meta) ──写──▶ Dexie
  └─ C LLM 层    enrichPhotoTags()        异步 · 联网 · 可失败
       成功 → mergeLlmTags → updateEntryTags(id, tags, 'llm')
       失败 → 什么都不做，保留 B 的结果
```

**底线**：A/B 永远离线可用；C 失败时 `tagSource` 保持 `'rule'`，绝不假装 LLM 答过
（与 `repo.ts`「此刻撒的谎以后就追不回来了」同一条纪律）。

- 唯一打标入口：`features/memory/extract.ts` 的 `deriveLocalTags`（repo 只调它）。
- 唯一写入口：`features/memory/repo.ts` 的 `addEntry`；回写用 `updateEntryTags`。

## 二 照片的信号从哪来

照片以前没有信号（`sceneHint` 硬编码，所有照片标签一样）。现在有三个来源：

| 来源 | 何时有 | 产出 | 文件 |
| --- | --- | --- | --- |
| **EXIF** | 相册上传的原始文件 | 拍摄时间（进时间流）、GPS、方向 | `features/capture/exif.ts`（手写解析，零依赖，只处理 JPEG） |
| **本地视觉特征** | 任何照片（快门/相册） | 亮度 / 色温 / 饱和度 → 一句中性画面描述（「夜里的暖光」）；dHash → 近似重复去重 | `features/capture/imageFeatures.ts` |
| **视觉 LLM** | 用户开启视觉时 | 真实画面描述 + **自由线索 clues** + themes/emotions/people/places | `features/memory/enrich.ts` |

- 相机路径走 `canvas.toBlob`，**EXIF 会丢**——只有相册来路带真实拍摄时间。
- 本地视觉**只产出 scene**，绝不借着像素猜心情（从亮度推不出「平静」）。
- 相册来的旧照片：**拍摄时间进时间流**（真实时间线），`meta.source='library'` 可区分。

## 三 相册是正式入口

「从相册选」与快门并列，不再是 `?lab=1` 的隐藏联调口。多张时按 dHash 折叠近似重复，
有 EXIF 按拍摄时间落、没有才错开。`?lab=1` 额外开的是拖图与多张提示（联调便利）。

## 四 隐私：这一条主动破了「记录不出设备」

视觉 LLM 是全项目**唯一**让记录离开设备的地方（[03](03-技术架构.md) 的隐私边界被有意突破）。
缓解：

1. **默认关**，需在采集页显式打开（`store.visionEnabled`）；关闭时 C 层整体短路。
2. 只发 **512px、JPEG 重编码**的缩图——`toDataURL` 天然剥掉 EXIF/GPS。
3. 代理不落盘、不留日志；带图请求默认用 `LLM_MODEL`（deepseek-v4.1 原生多模态）。
4. 内容级音频识别**尚未做**——先探测端点是否支持音频输入，支持才谈（`tools/probe_audio.mjs`）。

另一处边界不是隐私突破，而是**序列化纪律**：**Blob 永不落 `localStorage`**。
会话历史（`cike:sessions`）与所有 `cike:*` 键只存 JSON —— 记录里只有 `blobRef` 字符串，
真正的音视频／图片数据只在内存与 IndexedDB 的 `blobs` 表里。

## 五 按标签检索/整理

- `features/memory/query.ts`：`filterByTag` / `filterByScene` / `entryMatches` / `collectTagCandidates`。
  内存过滤（沿用 [db.ts](../app/src/features/memory/db.ts)「标签不建索引」的决定）。
- 守望的匹配（`data/watches.ts` 的 `watchMatches`）与 `entryMatches` **共用同一份实现**。
- `data/discoveries.ts` 的 `tagCardFrom`：标签值 → 一册，复用 `cardFromDef`（唯一成卡逻辑）。
- `data/collections.ts` 的**自建合集**：用户**自己挑**记录 → 一册。它存的是一份
  `entryIds` **快照**（不是判据），`origin: 'custom'`，同样经 `collectionCardFrom` 复用
  `cardFromDef`。**与守望刻意相反**：守望存判据、产出现算；合集存的就是**选择本身**——
  所以删合集＝删这条记录（「删除」），与守望「撤回无痕、产出保留」正好相对。
- 理解页自由输入：话里点到库里出现过的标签值 → 直接成册返回（本地、确定、不走 LLM），
  落点在 `store.aiVolumesFree`。

### 一个「此刻」是原子的（momentId）

首页的「记下此刻」是**攒元素再落下**：点文字/图片/声音各攒一个，长按才一次提交
（[docs/15](15-首页界面方案.md) §五）。一次提交里的几条记录共享一个 `Entry.momentId`
（`repo.addMoment`，一个 Dexie 事务写下整组）。

检索时，命中任一条就**把同组的其余一起带出来**——`query.expandToMoments(entries, hits)`：
取命中里出现过的 `momentId`，把那几组全部纳入，再并上没有 `momentId` 的命中。

只在**把命中聚成册**的地方用：`discoveries.ts` 的 `cardFromDef` 与 `watchCard`
（`cardFromVerdict` / `tagCardFrom` 都经由前者，自动覆盖）。
**不用在逐条渲染的时间流上**——那里展开会重复。

副作用是有意的：判据只命中照片（比如「出游」），同组那句心情并不匹配判据，
但它仍会被拉进册，甚至可能把条目数顶过 `MIN_ITEMS`。一个「此刻」不该被劈开看，所以这是对的。

> 相册一次连选多张也走 `addMoment`（一次导入本身就是一件事），不必再长按一次。

### 自由线索 clues：认识它的那一刻，把具体的东西留下

**问题**：受控词表让标签机器可用，但**会丢掉真正特殊的词**。实测被丢过的：
「自然风光」「排队」「山间栈道」。而长跨度合集的锚点恰恰是这些具体的物与事——
一个杯子从陌生到熟悉、孩子的每一个「第一次」——不是「出游 / 关系」这种类别。

**认识一张照片只有那一次机会**，当时没记下来就再也追不回来。所以：

- `EntryTags.clues: string[]`——**不受词表限制**的具体词（物、场合、动作），
  2–6 个字，模型一次能给出十几个（`enrich.ts` 的提示词明确要它「宁可多写」）。
- 四个维度里**装不下的词不丢**，由 `vocabulary.splitKnown` 切出来捞进 `clues`
  （`tags.schema.ts` 的 `parseLlmTags`）。丢弃只发生在「哪一维装它」，不发生在「要不要留」。
- 清洗只有几何约束：去空白、去重、单条 ≤16 字、一条记录 ≤12 条。**不查词表**。
- 检索时按**子串**（`query.entryMatches` 与 scene / text 同一个匹配面），
  与闭集标签的**整词相等**分开——所以 `collectClueCandidates` 与 `collectTagCandidates` 是两回事。
- 成卡走 `discoveries.clueCardFrom`（复用 `cardFromDef`），命中即成一册。

`clues` 也进提示词的**上下文**：`dossier` 的判定提示词里每条都带线索（「同一个马克杯出现在
几条里」比「都在家」有力得多），理解页的自由输入摘要里也带（模型据此把用户说的「杯子」
和自己记的「马克杯」联起来——**语义那一步只有模型做得了**，本地只做字面命中）。

**实测（2026-09-27，真模型 + 种子里的山景照片）**：

| 字段 | 结果 |
|---|---|
| scene | 「山间公路沿左侧延伸，右侧是深色木柱撑起的檐廊和木栏杆，栏杆间有石柱头；一名背对镜头的人背黄色包沿廊下步道走远。上方是蓝天和白云，远处为绿色山峦与树木。」 |
| **clues** | `["蓝天","白云","山峦","绿树","公路","黄色标线","木柱","木栏杆","石柱头","檐廊","深色屋顶","步道"]` |
| themes / places | `["出游"]` / `["山上"]`（受控词表照旧） |
| emotions / people | `[]` / `[]`（背对镜头的陌生人，不猜、不命名） |

理解页说「我留意过哪些缆车」→ 直接出「缆车」一册（本地、确定、不走 LLM）。

**为什么非要线索不可：一个长跨度的例子。** 种子里那个「门口那棵树」——
宿舍门口的一棵树，因为树皮上一道纹路被记住，后来记了秋天的风声、它发芽那天、
最近总在树边的白猫，跨了**十个月**。这一册的锚点是「树」这条线索。

- 类别维度里**根本没有「一棵树」这种东西**（themes 是 独处/工作/出游…
  places 是 家/公司/山上…）。塞不进去。
- 只按时间邻近也召回不了——十个月里相邻两条能隔几个月，`candidateGroups` 的
  6 小时断点会把它们切成十来个互不相干的碎片。
- 判据 `d-tree` 因此直接认线索：`e.tags.clues.some(c => c.includes('树'))`。

叙事也不写大段：册名一句（「门口那棵树」）+ 一句注 + 封面那行用**记录里最新的一句话本身**，
剩下的由文字与声音的时间线自己说。这就是「心情和时间的描述」该有的量。
谱系上它属于 [23 §四](23-发现档案与守望.md) 的「给证据不给结论」——
先材料，后结论，而这里连结论都只说一句。

故事**还在继续**：种子里给它加了一条今天的（`minutesAgo: 3`）。因此它是所有册里
最近发生过的一册，按「新的记录放在最上边」（[17](17-四屏界面方案.md) §四）排在发现页首位；
它的期间词也随之变成今天。想换回去，把那条的 `minutesAgo` 调大即可。

另外三个场景各留了一个**照片位**（树皮的纹路 / 秋天的树 / 树边的白猫）。
图片文件还没有时**不报错**：`seedIfEmpty` 拉不到就跳过，那一行照常落下、界面走降级渐变
（与相机不可用时同一条路）。把图放进 `app/public/seed/` 并命名为
`tree-bark.jpg` / `tree-autumn.jpg` / `tree-cat.jpg`，重开一次就是真图。

## 六 端点能力与还没做

**视觉 LLM 可用（2026-09-27 实测）**：QiyuanHub 的 `deepseek-v4.1` **原生多模态**，可直接读图
（[官方图片理解文档](https://www.qiyuanapi.cc/docs/vision)）。带图请求默认就用 `LLM_MODEL`，
**不需要**另配 `LLM_VISION_MODEL`（那是「换专门的多模态模型」的可选覆盖）。
实测：拿种子真照片打真请求，返回合法 JSON、严格遵守「不评价/不猜」提示词。

**内容级音频识别：暂时关闭**。端点协议上认识 `input_audio` 参数，但 `deepseek-v4.1` 不接受音频
（探测回「At most 0 audio(s) may be provided」），且模型目录里只有它一个。故这条按用户决定
的「支持才做」**留着不做**。探测脚本：`tools/probe_audio.mjs`。

> 注：模型目录 `GET /v1/models` 只列 `deepseek-v4.1`，一度被误读为「没有多模态」——
> 实际是这个模型本身多模态，能力不体现在模型数量上。以官方 `docs/vision` 为准。

## 七 两步成册（LLM 判定哪些值得成册）

**需求**：不是每个标签都该成一个合集——只有「有价值」的才成册，且**事件优先**。

分工（docs/23 §四 那条线的落地）：

| 步骤 | 谁做 | 内容 |
|---|---|---|
| **召回** | 本地、确定性 | [`dossier.ts`](../app/src/features/agent/dossier.ts) 的 `candidateGroups`：按**时间邻近**切组（相邻 >6h 就断），≥2 条才算候选。「事件」本质是有起止的一段时间，时间是最诚实的边界 |
| **判定** | LLM（串行队列） | `judgeGroup`：把每条记录的**描述 + 标签**（不重传图片）给模型，判「是不是一件事、哪类、叫什么」 |

**判定优先级**（写死在 `buildDossierPrompt`）：

1. `event` — 纯事件（爬山、看展、聚餐…）
2. `mixed` — 情绪 + 事件（「爬完山很累，但很松快」）
3. `worth:false` — 凑不成一件事 / 只是纯情绪 → **不成册**

**「有价值才成册」的落点就是 `worth:false`**：判定权交给模型，而不是本地拍一个阈值。

**产物是草稿**：判定通过 → `cardFromVerdict` 生成卡（复用 `cardFromDef`，`origin:'llm'`，
带 `kindType`）→ **草稿回执（留下 / 不要）**。AI 只有提议权。

**触发**：① 理解页说「整理…」且本地没命中已有册 → `store.aiDossier()`；② 一次导入 ≥3 条
且理解页已启动 → 自动跑一次。已判过的组记在 `store.dossierSeen`，不重复问、不重复付费；
判定失败**不标记**（下次可重试）。

**实测（2026-09-27，真模型）**：

| 输入 | 判定 |
|---|---|
| 一次爬山（4 条：栈道照片 + 山景照片 + 「累但风很舒服」+ 山风声音） | `worth:true, kind:"mixed", title:"去爬山那天"` ✓ |
| 零散三件事（加班 / 快递 / 环境声） | `worth:false` ✓ |
| 纯情绪无事件（提不起劲 / 闷） | `worth:false` ✓ |

## 八 并发上限与请求队列

端点**并发上限是 1 路**（QiyuanHub 赛事期）。实测：3 个并发请求 → 1 个 200、2 个 429
（`concurrency_limited`）。而「连拍几张照片 → 每条各发一个视觉请求」天然并发，不排队必撞。

所以所有 LLM 请求（照片打标 + 自由输入聊天）都过同一个**全局串行队列**
[`features/agent/llmQueue.ts`](../app/src/features/agent/llmQueue.ts)（`createQueue(1)`），
同一时刻只有一个在飞。

- **两条车道**：前台（聊天回复 / 成册判定，人在等）优先于后台（照片打标，可以等）。
  正在跑的那个不打断，优先级只决定排队顺序；同一车道内先来先服务。
- 视觉打标**带回退重试**：`rate-limited` / `timeout` / `network` 重试 2 次，重试期间
  占着槽位，不会再去抢并发。
- 前台聊天**不重试**：宁可早点回落 `FALLBACK_LISTEN`，别让用户干等。
- 队列满了就排队等，**不丢任务**；任务抛错也不占死槽位。

**边界**：这是**页内**队列，只管住当前页面/WebView。同一账号在多个标签页各开一个 App
时仍可能互撞上限——真要跨页串行得上 Web Locks 或服务端排队，现在不做。

## 九 AI 与确定性函数的职责划分

一句话：**AI 的自由度只花在「只有模型能做」的地方，其余全交给函数。**

| 环节 | 归谁 | 落在哪 |
|---|---|---|
| 意图路由（整理/查询） | 函数（正则） | `volumeIntent.ts` 的 `routeVolumeIntent` / `isOrganizeAsk` |
| 候选召回（哪些**可能**是一件事） | 函数（时间邻近） | `dossier.ts` 的 `candidateGroups` |
| 成卡（够不够 2 条、起止几号、卷结构） | 函数 | `discoveries.ts` 的 `cardFromDef` / `volumeOf` |
| 子集越界校验（模型给的序号） | 函数 | `dossier.ts` 的 `membersOf` |
| 自建合集（用户自己挑的 `entryIds` 快照） | 函数（无匹配，存的就是选择） | `collections.ts` 的 `listCollections` / `addCollection`（成卡经 `collectionCardFrom` → `cardFromDef`） |
| 守望 / 标签检索 / 线索检索 | 函数（子串） | `watches.ts` / `query.ts`（线索单开 `collectClueCandidates` + `clueCardFrom`） |
| **标签词表** | 函数 | `vocabulary.ts`（见下） |
| 语气 / 长度 / 去引号 | 函数 | `prompt.ts` 的 `sanitizeReply` |
| **这条记录是什么**（画面 / 具体的物 / 主题 / 情绪 / 人物） | **AI**（视觉） | `enrich.ts` 的 `enrichPhotoTags` |
| **这些是不是一件事 / 叫什么 / 哪类 / 挑哪些** | **AI** | `dossier.ts` 的 `judgeGroup` |
| **怎么回一句话** | **AI** | `freeText.ts` 的 `askFreeText` |

### 受控标签词表（`features/memory/vocabulary.ts`）

**为什么**：标签是机器用的——本地判据（`themes.includes('出游')`）、守望匹配、聚合计数全按
固定词比较。而模型自由发挥的词（实测出现过「自然风光」「排队」「山间栈道」）**永远命中不了
本地判据**，视觉打标就白做。

**怎么切**：
- 四个机器维度（themes / emotions / people / places）收进**封闭词表**，规则提取与 LLM 提取
  都只能产出表内的值；
- `scene` 与 **`clues`** **不设限**——一个是给人读的描述，一个是给机器搜的具体线索；
- 校验分两层：**形状严格**（少字段即判失败回落规则；只有 `clues` 允许缺，因为「没有额外线索」
  不是「没答上来」）+ **取值过滤**（表外的词从那个维度剔掉，但**捞进 `clues`，不丢**）。

> 一句话：**词表管的是「哪一维装它」，不是「要不要留它」。** 早期版本把表外词直接丢掉，
> 换来了判据命中，代价是丢掉了这张照片最特别的部分——现在两样都要。

**实测（2026-09-27，真 App 全链路：开视觉 → 相册选图 → 读回标签）**：

| 字段 | 早期（直接丢掉） | 现在 |
|---|---|---|
| scene | 「雾气中的木栈道…」 | 更详实的一句（提示词改成「看得见就写下来」，不再是「拿不准就少写」） |
| themes | `["自然风光","旅行","排队","山间栈道"]` → `["出游"]` | `["出游"]` ✓（表外的词去 `clues`） |
| places | `["山区景区","山间"]` → `["山上"]` | `["山上"]` ✓（同上） |
